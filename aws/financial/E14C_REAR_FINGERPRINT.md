# E14C — Rear fingerprint parity

Recorded 2026-09-22T23:45Z. Money flags stayed **OFF**. Selected check was **not** mutated. No FinCapture.

## Root cause

`endorsed_deposit_9ffq.checkalt.jpg` was generated by the **browser** `EndorsementAdjuster` (`src/components/checks/EndorsementAdjuster.tsx` + `renderDepositImage` / `canvas-v2`), not the AWS compositor.

Evidence:

- Live meta keys: `request_id`, `renderer_version`, `mime_type`, `width`, `height`, `bytes`, `override` — the browser persist payload.
- Filename token `9ffq` is `(Date.now() % 1_000_000).toString(36)` from the adjuster. AWS composite uses `randomBytes(4).toString('hex')` (8 hex chars, no `q`).
- AWS compositor meta would include `engine`, `sha256`, `original_back_image_path` and then `stampCheckAltRearFingerprint`.

The **normal production Adjust Received Endorsement** dialog does not call `composite-endorsement-signatures`. That function is used by print/export (`ensureDepositReadyBackImage`) and after a genuine sign (`afterGenuineEndorsementSigned`).

`checkalt_rear_fingerprint` is written only by:

1. `endorsement-composite.mjs` after AWS composite
2. `storage-write.mjs` `stampOfficialRearFingerprintIfNeeded` when the upload path already equals `toCheckAltPath(back_image_deposit_path)`

Neither runs for a **new** `endorsed_deposit_*.checkalt.jpg`:

- At upload time `back_image_deposit_path` is still null / old, so storage-write does not stamp.
- The adjuster then `UPDATE`s `endorsement_render_meta` without a fingerprint. Even if storage had stamped, this replace would wipe it.

`evaluateProductionDepositEligibility` / `evaluateRearImageFreshness` are still correct. The fingerprint binds the official rear to current endorsement state (ids, types, statuses, `signed_at`). It is not stale-contract leftover. Do not remove it. Do not let the browser author it.

Staging/AWS deposit-image parity already stamps on the compositor path (`aws/tests/endorsement-deposit-image-parity.test.mjs`). Production Adjust used the browser path, so the stamp never ran.

## Fix

Smallest general correction: when `/data/write` persists `back_image_deposit_path` to an official `.checkalt.jpg` (Adjust generate or approve), the API:

1. Strips any client-supplied `checkalt_rear_fingerprint`
2. Stamps the server hash from current payees/endorsements
3. Fails closed (`503 provider_rear_fingerprint_stamp_failed`) if the stamp cannot be written

Clear/reset (`deposit path` / meta `null`, status `idle`/`failed`) does not stamp. Reupload Replace Back still clears official rear + meta so a leftover artifact cannot stay eligible.

Eligibility contract unchanged. No one-off stamp on this check.
