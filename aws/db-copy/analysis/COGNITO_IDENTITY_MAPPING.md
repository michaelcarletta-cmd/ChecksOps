# Cognito identity mapping design (planning only)

Do **not** create or import Cognito users in this pass. Do **not** point the API at database `checksops`. Do **not** restore the 47 `auth.users` FKs yet.

Existing staging Cognito user pool `checksops-staging` (from the SAM stack) is the future IdP. Application identity stays the 9 Supabase user UUIDs already stored in restored public tables.

## Goal

Cognito authenticates. ChecksOps authorization and all existing rows keep using the **application user UUID** (`auth.users.id` / `profiles.id`). Cognito `sub` is a login identifier only. Never overwrite `profiles.id`, `tenant_users.user_id`, `user_roles.user_id`, or audit actor columns with `sub`.

## Why not use Cognito `sub` as the app user id

Cognito assigns a new UUID `sub` at user creation. Replacing application UUIDs would rewrite `profiles` (8 rows), `tenant_users` (7), `user_roles` (10 role rows / 9 users), and every populated audit column among the 47 deferred FKs. That is a data rewrite, not an auth cutover. The dump already has a stable UUID for each of the 9 users.

## Mapping table (source of truth)

Add later (not now) a dedicated table, not a PK change on `profiles`:

```sql
CREATE TABLE public.identity_accounts (
  application_user_id uuid PRIMARY KEY,
  cognito_sub text NOT NULL UNIQUE,
  email citext,
  status text NOT NULL DEFAULT 'pending',
  linked_at timestamptz,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

| Column | Meaning |
| --- | --- |
| `application_user_id` | Existing Supabase `auth.users.id`. Same value as `profiles.id` when a profile exists. |
| `cognito_sub` | Cognito JWT `sub` after the user is created in the pool. Empty/`pending` until import. |
| `email` | Match key for a later invite/import. Not a password. |

Optional later: Cognito custom attribute `custom:application_user_id` as a cache of the same UUID. The table remains authoritative.

Do not put Cognito `sub` into `profiles.id`.

## How each identity field is used

### Existing Supabase user UUID

The 9 distinct UUIDs already present across restored public columns (union of the 47 deferred FK columns). 8 have `profiles` rows; 9 appear in `user_roles`; 7 appear in `tenant_users`. The user with roles and no profile still keeps that UUID; a later import can add a `profiles` row with the **same** id if needed. Do not mint a new id.

### Cognito `sub`

Generated by Cognito when the user is created (invite or admin create). Stored only on `identity_accounts.cognito_sub`. Used to look up `application_user_id`. Never stored in audit/user-id columns.

### `profiles.id`

Stays the existing UUID (PK). Today it was `REFERENCES auth.users(id) ON DELETE CASCADE`. After Auth cutover, retarget that FK to nothing Cognito-related: either drop it or point it at `identity_accounts.application_user_id` / keep PK without an `auth.users` FK. Do not change the 8 id values.

### `tenant_users.user_id`

Stays the existing UUID. 7 rows, `ON DELETE CASCADE` to `auth.users`. Later retarget FK to `profiles.id` (same UUID). Membership and `tenant_role` stay on this table. Do not rewrite `user_id` to `sub`.

### `user_roles.user_id`

Stays the existing UUID. 10 rows for 9 users (`ON DELETE CASCADE`). Later retarget FK to `profiles.id`. App roles (`admin`/`staff`/…) stay here. Authorization reads this table using `application_user_id`, never Cognito groups as the source of truth.

### Audit / actor columns (40 remaining deferred FKs)

`created_by`, `uploaded_by`, `actor_id`, `sent_by`, `authorized_by`, etc. Values already in the dump are application UUIDs (25 columns have data; 20 are empty). Leave historical values unchanged. New writes from the AWS API use `application_user_id` from the mapping, not `sub`. Later FKs should reference `profiles.id`.

## API translation: Cognito identity → ChecksOps UUID

Current `auth.uid()` on RDS is a stub that returns NULL. After Auth is wired (later):

1. Client signs in to Cognito (SRP / hosted UI). Frontend already has pool/client env placeholders (`VITE_COGNITO_USER_POOL_ID`, `VITE_COGNITO_USER_POOL_CLIENT_ID`).
2. API receives `Authorization: Bearer <Cognito ID token>`.
3. Verify the JWT (signature, `iss` = this user pool, `aud` = web client, `exp`, token_use = `id`). API Gateway JWT authorizer or Lambda verifier; do not trust unverified claims.
4. Read `sub` (and `email` if present).
5. `SELECT application_user_id FROM identity_accounts WHERE cognito_sub = $sub AND status = 'active'`.
6. If no row → 401. Do not auto-insert a new application UUID for these 9 users.
7. Put `application_user_id` on the request (authorizer context). All SQL, `user_roles`, `tenant_users`, and audit inserts use that UUID.
8. For the 40 functions that call `auth.uid()`, replace the NULL stub with a session GUC, for example `SET LOCAL request.app_user_id = '<application_user_id>'`, and `auth.uid()` returns `current_setting('request.app_user_id', true)::uuid`. That GUC is the **application** UUID, not Cognito `sub`.

```
Cognito ID token
  sub  ---------------------->  identity_accounts.cognito_sub
                                  |
                                  v
                                application_user_id  ==  profiles.id
                                                     ==  tenant_users.user_id
                                                     ==  user_roles.user_id
                                                     ==  audit actor UUIDs
                                  |
                                  v
                                auth.uid()  / request context
```

Authorization stays in the database (`user_roles`, `tenant_users`), not in Cognito groups or client-side role claims.

## Later import (not this pass)

When approved:

1. Build the 9 `identity_accounts` rows from restored public UUIDs + emails (operator-held; do not dump password hashes, sessions, or MFA).
2. Create Cognito users **by email** with force-change-password / invite. Do not import Supabase password hashes.
3. Write each new `sub` into `identity_accounts`.
4. Retarget the 47 FKs from `auth.users(id)` to `profiles(id)` (same UUID). Do not FK to Cognito.
5. Point `auth.uid()` at the GUC as above.
